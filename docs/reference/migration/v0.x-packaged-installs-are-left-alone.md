# v0.x: the pre-run check leaves a package-managed install alone

`update` already refused to replace a binary that Homebrew, dpkg or rpm owns. The check that runs before a command did
not know about them, so it still asked the user to run `update`, and under the `enabled` policy blocked a command at
each check until they did. Nothing in a tool's code changes
([spec 0097](https://gitlab.com/phpboyscout/go-tool-base/-/wikis/specs/0097-linux-package-signing) D7).

## What changes

For an install a package manager owns:

- **No pre-run update check.** No release probe, and no prompt.
- **The `enabled` policy does not block it.** Nor does an unattended run warn that the policy was not enforced.
- **No out-of-date reminder.** The "a newer ... is available" warning is gone, including for a version cached before
  you upgraded gtb.

`update` still refuses, and names the manager's own command. An install in `$HOME/.local/bin` or `/usr/local`, outside a
Homebrew Cellar or Caskroom, is checked as before.

## What to check

- A tool that relies on the `enabled` policy to keep its users current cannot rely on it for a Homebrew, dpkg or rpm
  install. Their package manager decides when they upgrade.
- A binary under `/usr`, `/bin`, `/sbin` or `/opt` runs `dpkg-query`, and `rpm` if that finds nothing, when a check is
  due at a terminal. So does a service, cron job or script under the `enabled` policy, when a check is due and it is
  not under CI. Each is given six seconds at most. With no check made, none is ever recorded, so for an install dpkg or
  rpm owns that is every command the check covers (about 0.06 seconds for `dpkg-query` on one Ubuntu machine).
