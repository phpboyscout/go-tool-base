# `gtb set` / `gtb unset` / `gtb get`

One setter over the manifest's author settings. The path is the manifest's own
dotted path; the `properties.` prefix may be left off.

```bash
gtb set chat.default.provider openai
gtb set telemetry.endpoint https://telemetry.example.internal
gtb set bootstrap.skip_config_check version doctor     # a list: several values, or comma-separated
gtb set bootstrap.auto_initialise true                 # a bool: true or false
gtb set release_source.repo neworg/newname             # org/name, spread over owner and repo
gtb set version.go 1.27
gtb unset chat.default.model
gtb get chat.providers                                 # one value per line
```

## What happens on `set`

1. The path is resolved against the author-settings table
   (`cli/pkg/generator/author_settings.go`). A path the table does not name is
   refused with the list of settable paths.
2. The value is written into the manifest in memory and the whole manifest is
   validated the way `regenerate` validates it, which is the way the generate
   flags are validated. A refused value writes nothing.
3. The derived files are synced (root command, adapter files, signing files,
   derived fields), and so is every skeleton file the change moves: the CI
   file, `.goreleaser.yaml`, `zensical.toml`, `.golangci.yaml`, `.mockery.yml`
   and the release scripts. A file the change stops producing (the cask push
   script when the tap goes) is removed. Then the manifest is written, and on a
   real filesystem the touched files are formatted. No `regenerate` is needed
   afterwards.

Only files whose render the change itself moves are written. A project last
generated by an older gtb keeps its other template differences until you run
`gtb regenerate project`
([spec 0218](https://gitlab.com/phpboyscout/go-tool-base/-/wikis/specs/0218-gtb-set-brings-every-file-a-setting-feeds-up-to-date)).

### A file you have edited

A skeleton file whose content is not what gtb last wrote is yours, so `set`
leaves it, warns, and still succeeds:

```text
.goreleaser.yaml was edited by hand, so it was left as it is; gtb regenerate project shows the change and asks
```

A file gtb has no record of writing counts as edited, as it does under
`regenerate`. The same holds for a file the change would remove. A path in
`.gtb/ignore` is never written. The README, the justfile, the docs landing page
and the init assets are yours after the first render and are never rewritten.
A project with template overlays leaves the overlay's files, and any file an
overlay may have replaced, to `gtb regenerate project`.

The skeleton files are written before the manifest records their hashes. If
`set` is interrupted between the two, those files look edited by hand; run the
same `set` again and it records them.

## Refused paths

| Path | Why | Use instead |
|---|---|---|
| `features` | features have their own verbs | `gtb enable <feature>`, `gtb disable <feature>` |
| `templates` | overlays have their own verbs | `gtb template add`, `update`, `remove` |
| `properties.config.file_only` | the file-only list is edited in the manifest alone | edit `.gtb/manifest.yaml` and run `gtb regenerate project` |
| `hashes`, `commands`, `docs_layout`, `module_published`, `version.gtb` | recorded by the generator | nothing; they describe what gtb did |

## Flags

| Flag | Default | Description |
|---|---|---|
| `--path, -p` | `.` | Project root. |

## Settable paths

Every "recorded as" field in the [generate reference](generate.md) is settable,
and so is `generator.ai`, which has no generate flag because `--ai` is the
run's own ask: `true` lets gtb call a model when generating the project, `false`
refuses, and `gtb unset generator.ai` defers to your `gtb init` choice
([spec 0211](https://gitlab.com/phpboyscout/go-tool-base/-/wikis/specs/0211-ai-generation-is-an-explicit-choice)).
The list `gtb set` prints on an unknown path is generated from the
table and is the authority. Spec
[0197](https://gitlab.com/phpboyscout/go-tool-base/-/wikis/specs/0197-author-settings-as-one-surface)
D6.
