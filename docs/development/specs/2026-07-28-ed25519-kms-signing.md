## 1. The real problem (the ticket's framing was the wrong target)

### 1.1 What the maintainer actually needs

Sign **Rust `cargo-bin` (precompiled-binary) release artifacts** with Ed25519,
in a form the **Rust consumers can verify**. The primary consumer is
`rust-tool-base`'s self-update verifier, `rtb-update`. `ffmpeg-wasi` and any
future non-Go tool that reuses the ecosystem's release-signing pattern are
secondary consumers with the same shape of requirement.

### 1.2 Why issue #5's framing does not get there

Issue #5 is titled *"support Ed25519 KMS keys — the RSA-only constraint has
expired"* and proposes an **additive Ed25519 branch on the existing OpenPGP +
AWS-KMS backend**: teach `signing-aws-kms` to accept an `ECC_NIST_EDWARDS25519`
key and have `go/signing`'s `openpgpkey.DetachSign` emit an OpenPGP-Ed25519
detached signature over `checksums.txt`.

That is a correct and worthwhile piece of housekeeping **for GTB's own Go
self-update path**, which speaks OpenPGP. But it does **not** unblock the Rust
consumer, on two independent axes:

1. **Container mismatch.** `rtb-update` verifies a **raw 64-byte PureEd25519
   detached signature** (`.sig`) or a **minisign `.minisig`** — and even for
   minisign, *only* the pure "Ed" variant. It has **no OpenPGP parser**. GTB's
   signing stack emits **ASCII-armored OpenPGP packets** (`openpgpkey`
   →`openpgp.DetachSign` → `armor.Encode`; confirmed in
   `go/signing/openpgpkey/sign.go` and `internal/cmd/sign/sign.go`). An
   OpenPGP-Ed25519 signature is still an OpenPGP packet the Rust verifier cannot
   read. Adding Ed25519 *inside* the OpenPGP container does not change the
   container.

2. **Scope/size mismatch.** `rtb-update`'s producer contract
   (`docs/how-to/secure-releases.md`) asks for *"an Ed25519 detached signature
   **over the archive**"* — the whole multi-megabyte artifact. **AWS KMS cannot
   produce a pure Ed25519 signature over a multi-MB message** (see §2.2): the
   `RAW` (pure) mode is capped at 4096 bytes, and the `PH` mode is a *different
   algorithm* (Ed25519ph / HashEdDSA) that the Rust "Ed"-only path explicitly
   rejects.

So the honest conclusion is: **the ticket solves a real but adjacent problem.**
"Ed25519 in the OpenPGP+KMS backend" produces an artifact for GTB's own
OpenPGP-based verifier, not for `rtb-update`. Serving the Rust consumer is a
**format-and-custody** question that the ticket's framing skips over. This spike
re-aims at that question.

### 1.3 What this spike decides

- **Confirm the external facts** that bound the design (KMS Ed25519 modes and
  the 4 KB cap; what `cargo-binstall`/minisign actually require; the go-crypto
  opaque-signer gap). — §2.
- **Evaluate three resolution options** against the one thing the current design
  exists to protect: **HSM custody** (private key never leaves KMS; OIDC-assumed
  role). — §3.
- **Assess a standalone signing CLI** as the right long-term home for a
  multi-format signing surface now that signing is cross-project. — §4.
- **Sketch the cross-repo work** for the recommended direction. — §5.
- **Surface the maintainer decisions** — the custody fork and the standalone-CLI
  go/no-go, plus rotation timing against the in-flight rekey. — §6.

## 2. Ground truth (confirmed external facts + the consumer contract)

### 2.1 The `rtb-update` verifier contract (read from source)

From `rust-tool-base/crates/rtb-update/src/verify.rs` and
`docs/how-to/secure-releases.md`:

- **Two on-wire formats**, selected by the signature file's extension:
  - `.sig` — **64 raw bytes**, the Ed25519 signature itself.
  - `.minisig` — minisign text format; the first base64 line decodes to
    `[algo:2][key_id:8][signature:64]` = 74 bytes.
- **Pure Ed25519 only.** The signature is verified with `ed25519-dalek`'s
  `VerifyingKey::verify(asset_bytes, &sig)` — i.e. **PureEd25519 over the whole
  asset**. For the minisign path, the 2-byte algorithm id **must be `"Ed"`**
  (pure); the `"ED"` prehashed-BLAKE2b variant is **rejected with a clear
  error**. This is a hard, deliberate constraint, not an incidental one.
- **Keys are raw.** `ToolMetadata::update_public_keys` is `Vec<[u8; 32]>` — a
  set of raw 32-byte Ed25519 public keys, **any-one-verifies** to support
  rotation without breaking deployed binaries.
- **Plus a SHA-256 checksums path.** `verify::checksums()` parses a
  `sha256sum`-format file (`"<hex>  <filename>"` per line) and matches the
  asset by basename. The producer contract publishes a `.sum` alongside every
  archive; the updater verifies **both** signature and checksum before swapping.

There is **no OpenPGP anywhere** in this path, and there is **no existing path
that verifies a signature over the checksums file itself** — today the signature
is over the *archive* and the checksums file is verified per-*archive* by hash.
That gap matters for Option A (§3.1).

### 2.2 AWS KMS Ed25519 — modes and the 4 KB cap (CONFIRMED)

Confirmed against the AWS KMS key-spec reference and the `Sign` API docs (Nov
2025 Edwards-curve GA):

| Signing algorithm | `MessageType` | FIPS 186-5 | Semantics |
|---|---|---|---|
| `ED25519_SHA_512` | **`RAW`** | §7.6 EdDSA | **PureEd25519** over the message. **Message capped at 4096 bytes.** |
| `ED25519_PH_SHA_512` | **`DIGEST`** | §7.8 HashEdDSA | **Ed25519ph** — a *different algorithm*. |

Two facts are decisive and both are confirmed verbatim in AWS docs:

1. **The RAW (pure) message is capped at 4096 bytes.** Exceeding it returns
   `ValidationException … Value at 'message' failed to satisfy constraint:
   Member must have length less than or equal to 4096`. So KMS **cannot**
   PureEd25519-sign a multi-MB archive directly.
2. **PH is not a size escape hatch for the pure algorithm — it is a different
   algorithm.** The AWS key-spec reference states that with `ED25519_PH_SHA_512`
   + `DIGEST`, *"AWS KMS still performs the SHA-512 prehash … the input is
   hashed twice."* That is HashEdDSA (Ed25519ph), which produces a signature
   over `SHA-512(message)` bound with the Ed25519ph domain separator — **not**
   the PureEd25519 signature that `ed25519-dalek`'s `verify()` (and minisign
   "Ed") checks. The two message types **"cannot be used interchangeably"** (AWS
   wording). A PH signature handed to `rtb-update` fails verification.

**Net:** KMS Ed25519 can only produce a signature the Rust side accepts when the
signed message is **≤ 4096 bytes** — i.e. a small **manifest**, never the
archive. Custody (private key in the HSM) is preserved either way; the size
ceiling is the binding constraint.

References:
:   AWS KMS Edwards-curve GA announcement
    (<https://aws.amazon.com/about-aws/whats-new/2025/11/aws-kms-edwards-curve-digital-signature-algorithm/>),
    KMS key-spec reference
    (<https://docs.aws.amazon.com/kms/latest/developerguide/symm-asymm-choose-key-spec.html>),
    KMS `Sign` API `MessageType`
    (<https://docs.aws.amazon.com/kms/latest/APIReference/API_Sign.html>).

### 2.3 `cargo-binstall` / minisign reality (CONFIRMED)

- `cargo-binstall`'s **only** supported signing algorithm is **minisign**,
  configured per-crate under `[package.metadata.binstall.signing]` with
  `algorithm = "minisign"`, `pubkey = "<minisign pubkey>"`, and an optional
  `file` URL template. Signatures are **per-artifact `.sig`** files
  (`minisign -S -W -s signing.key -x pkg.tar.zst.sig -m pkg.tar.zst`).
  Source: `cargo-binstall/SIGNING.md`.
- **Minisign's default is the *prehashed* ("ED", BLAKE2b-512) variant.** The
  `cargo-binstall` example command passes no `-H`/legacy flag, so it produces
  the default **prehashed** signature. `-W` only disables the secret-key
  password prompt; it is not about prehashing.
- **This is the opposite of what `rtb-update` accepts.** `rtb-update` accepts
  **only** the pure "Ed" variant and **rejects** prehashed "ED". So the two Rust
  consumers want **mutually incompatible** minisign variants — a single
  signature cannot satisfy both. Source: minisign format docs
  (<https://jedisct1.github.io/minisign/>).
- **Minisign is not a KMS-friendly format.** A `.minisig` carries a *second*
  signature — the **global signature** `ed25519(<signature> || <trusted
  comment>)` — which requires the secret key **again**. And the prehash is
  **BLAKE2b-512**, which KMS does not offer (KMS PH is SHA-512). So KMS cannot
  produce a standard prehashed `.minisig` at all, and could only ever assemble a
  *pure* one for a **≤ 4 KB** input via two RAW-Sign calls — never over an
  archive.

**Answer to the maintainer's question:** `cargo-binstall` is **not currently a
served target** — it wants prehashed minisign, which conflicts with
`rtb-update`'s pure-only rule and cannot come from KMS. Treat **`rtb-update` as
the single primary consumer** for this work. `cargo-binstall` support, if ever
wanted, is a *separate* software-minisign side-channel (§3.2, Option B) and
would require `rtb-update` to also accept prehashed — a Rust-side decision, out
of scope here.

### 2.4 The go-crypto opaque-signer gap (CONFIRMED, relevant to Option A/C)

Even where the OpenPGP container *is* wanted (GTB's own Go self-update, or a
KMS-signed manifest kept in OpenPGP), driving **KMS-Ed25519 through go-crypto's
OpenPGP signing is blocked** in go-crypto v1.4.1: the `PubKeyAlgoEd25519` /
`PubKeyAlgoEdDSA` branches of `openpgp/packet/signature.go` **hard type-assert a
concrete `*ed25519.PrivateKey`** with no `crypto.Signer` fall-through (unlike
the RSA/ECDSA branches). An opaque KMS `crypto.Signer` is not that concrete
type, so the assertion fails. This affects both minting and detached-sign.
Resolving it needs either an upstream go-crypto contribution or in-module manual
packet assembly — a real, security-sensitive piece of work, **not "just test
coverage"** as issue #5 supposed. It is only on the critical path for options
that keep OpenPGP framing; the raw-Ed25519 manifest path (§3.1) sidesteps it
entirely by not using OpenPGP for the Rust-facing signature.

## 3. Three resolution options, evaluated against custody

The current design exists to guarantee **custody**: the release private key
never leaves the KMS HSM boundary, and signing is an OIDC-assumed-role
round-trip with the key policy as the single grant surface. That guarantee is
the axis every option is judged on.

### 3.1 Option A — keep KMS custody, sign a checksums **manifest**

**Shape.** KMS PureEd25519-signs a **`checksums.txt` manifest** (well under
4 KB even for a large target matrix). GTB publishes the archive set, the
manifest, and a **raw 64-byte `.sig` over the manifest**. `rtb-update` verifies
the **manifest signature** once, then verifies each downloaded **archive's
SHA-256 against the manifest**.

**Custody.** **Fully preserved.** The signed message (the manifest) is ≤ 4 KB,
so KMS `ED25519_SHA_512` + `RAW` applies directly and produces a genuine
PureEd25519 signature — exactly the "Ed" primitive `rtb-update` already checks,
just over the manifest rather than the archive. Private key stays in the HSM;
OIDC role unchanged.

**GTB-side work.** New: emit a **raw 64-byte Ed25519 `.sig`** (not
OpenPGP-armored) over the manifest. This is the genuinely new capability — the
signing stack today only emits OpenPGP armor. It can live as a new output mode
on `go/signing` / `gtb sign` (a "raw detached Ed25519" sink) and does **not**
touch the go-crypto OpenPGP gap (§2.4), because the Rust-facing signature is not
OpenPGP. Requires the `signing-aws-kms` Ed25519 branch from issue #5 (accept the
`ECC_NIST_EDWARDS25519` key, call `ED25519_SHA_512`/`RAW`) — but wired to a raw
sink instead of `openpgpkey`.

**rust-tool-base work.** `rtb-update` already has **both primitives** — the
`ed25519()` verifier and the `checksums()` parser — but currently composes them
as *"sig over archive"* + *"checksum of archive"*. Option A recomposes them as
**"sig over manifest, then checksum of each archive against the manifest."**
This is a contained change to `verify.rs`/`command.rs` and a **producer-contract
change** in `secure-releases.md` (from "Ed25519 signature over the archive" to
"Ed25519 signature over the SHA-256 manifest"). The `Vec<[u8;32]>` any-one
rotation model is unaffected.

**Trade-offs.**
- Pro: **preserves HSM custody** (the whole point of the current programme).
- Pro: reuses GTB's existing manifest model — `gtb sign` already signs
  `checksums.txt` for the Go path.
- Pro: sidesteps the go-crypto opaque-Ed25519 blocker entirely.
- Pro: one signature covers the whole release (manifest), not per-artifact.
- Con: **changes the Rust consumer's trust contract** (sig over manifest, not
  archive). Modest, but it is a real cross-repo change and a security-relevant
  one — the manifest becomes the root of trust, so its integrity (one signature)
  now gates every archive's checksum.
- Con: does **not** serve `cargo-binstall` (needs per-artifact prehashed
  minisign) — but §2.3 shows nothing can serve both consumers at once anyway.

### 3.2 Option B — keep the per-artifact model, use a **software** Ed25519 key

**Shape.** A software Ed25519 key materialised in CI signs **each archive**
whole-file (PureEd25519), matching the minisign convention and `rtb-update`'s
*current* contract exactly (per-artifact `.sig`/`.minisig` over the archive). No
KMS involvement for the Rust artifacts.

**Custody.** **Downgraded, honestly.** The private key exists as bytes in the CI
runner at signing time. Mitigations (short-lived CI secret, OIDC-fetched from a
secrets manager, sealed to a protected branch, rotated frequently) reduce but do
**not** eliminate exposure: a compromised runner or a malicious pipeline step
can exfiltrate the raw key. This is precisely the property the KMS design was
built to avoid. It is a genuine step down from "key never leaves the HSM," and
must be named as such, not glossed.

**Work.** Smallest cross-repo footprint: **no** `rtb-update` change (its current
contract is met), **no** go-crypto work, **no** KMS backend change. GTB/CI grows
a software-minisign (or raw-Ed25519) signing step. It is *also* the only option
that could serve `cargo-binstall` (a software minisign key can produce the
prehashed `.minisig` `cargo-binstall` wants) — though that still needs
`rtb-update` to accept prehashed, or a second signature.

**Trade-offs.**
- Pro: matches the existing Rust contract with zero Rust change; smallest total
  work; only option compatible with `cargo-binstall`.
- Pro: whole-archive signatures (strongest artifact-integrity story — the
  signature covers the bytes directly, no manifest indirection).
- Con: **custody downgrade** — raw key in CI. For a self-updating tool that
  swaps its own binary, the signing key is a high-value target; this is the
  decision's crux.

### 3.3 Option C — hybrid (KMS-RSA/OpenPGP for GTB's manifest; software Ed25519 for Rust/cargo-bin)

**Shape.** Keep the existing **KMS-RSA-over-OpenPGP** path exactly as-is for
GTB's own Go self-update manifest (no change, no go-crypto risk), and add a
**software Ed25519** side-channel *only* for the Rust/`cargo-bin` artifacts.

**Custody.** **Mixed.** GTB's Go releases keep full HSM custody; the Rust
artifacts inherit Option B's software-key downgrade. The blast radius of the
software key is scoped to the Rust consumer.

**Trade-offs.**
- Pro: zero disruption to the proven GTB path; isolates the custody downgrade to
  where it is unavoidable under the current Rust contract; unblocks Rust fastest.
- Pro: could also carry the `cargo-binstall` minisign channel.
- Con: **two key-custody models and two signing toolchains** to operate,
  document, and rotate — permanent operational drag, and two things to get
  wrong. Contradicts the "one signing programme" direction the standalone-CLI
  idea (§4) is reaching for.
- Con: still leaves the Rust key in CI — it does not *solve* custody, it
  *contains* it.

### 3.4 Recommendation — **Option A**, with the custody trade-off flagged for the maintainer

**Recommend Option A** (KMS-custody, sign a manifest), because it is the only
option that **keeps the HSM-custody guarantee the current programme was built
around** while still producing a signature `rtb-update` can verify. It reuses
GTB's manifest model, sidesteps the go-crypto Ed25519 blocker, and asks
`rtb-update` for a contained, well-scoped contract change it is already
90 %-equipped for (it has both the ed25519 and checksums primitives).

The cost is real and must be a **maintainer decision, not an author default**:
Option A moves the Rust consumer's root of trust from "a signature over each
archive" to "a signature over the manifest that vouches for each archive's
hash." That is standard practice (it is how Sigstore/GoReleaser/Debian-style
manifests work) and the manifest signature is still PureEd25519 in the HSM — but
it *is* a change to what the Rust side trusts, so the maintainer owns it.

**Reject Option B** as the default because the custody downgrade (raw key in CI)
discards the central property of the existing design for a self-updating tool
whose key is a high-value target. Keep it available only if the maintainer
decides the per-archive whole-file guarantee and/or `cargo-binstall`
compatibility outweigh custody — an explicit, eyes-open trade.

**Treat Option C as the fallback** if `rtb-update` cannot take the
manifest-contract change on an acceptable timeline: it unblocks Rust without
touching the GTB path, at the cost of running two custody models indefinitely.

## 4. Standalone signing CLI — architecture assessment

**Context.** Signing is now genuinely cross-project: `go-tool-base` (Go
self-update), `rust-tool-base` (Rust self-update), and `ffmpeg-wasi` (already
reuses `gtb sign` wholesale). The maintainer asks whether the signing command
tree should become its **own standalone CLI/module** that GTB *imports* — so
`gtb sign` keeps working for GTB projects, but the signing surface also lives as
a project consumable by non-Go and non-GTB tools, and becomes the single home
that solves the Ed25519/manifest/multi-format question once.

**What already is and isn't extracted.** The two *libraries* are **already
standalone published modules**: `gitlab.com/phpboyscout/go/signing` (the
`openpgpkey` container + `verify`) and
`gitlab.com/phpboyscout/go/signing-aws-kms` (the KMS `crypto.Signer` backend),
pinned in GTB's `go.mod` at `v0.2.2` / `v0.2.5`. What is **not** extracted is the
**command tree** — `internal/cmd/sign/` and `internal/cmd/keys/` (`sign`, `keys
mint`, `keys generate`, `keys wkd`) — which lives inside GTB's `internal/` and
is therefore **not importable** by other projects. `ffmpeg-wasi` reuses it only
by building a GTB binary.

**In scope to extract.** Only the **command tree** needs to move — a thin new
CLI module, provisionally `gitlab.com/phpboyscout/go/signctl` (name TBD), that:

- wraps the existing `go/signing` + `go/signing-aws-kms` libraries (no library
  re-extraction — they are already modules);
- exposes `sign` / `keys` as Cobra command constructors **and** ships a
  standalone binary (`go install …/signctl@latest`), so non-GTB/non-Go release
  pipelines can sign without a GTB build;
- is the natural home for the **new multi-format output surface** this spike
  implies: OpenPGP-armored (GTB/Go), **raw 64-byte Ed25519** (rtb-update
  Option A), and — if ever wanted — software **minisign** (cargo-binstall,
  Option B). One place to get the format matrix right, tested once.

**How GTB re-imports it.** Exactly like the other extracted modules: GTB depends
on `signctl`, and `internal/cmd/root` registers `signctl.NewCmdSign(p)` /
`signctl.NewCmdKeys(p)` so `gtb sign` / `gtb keys` are unchanged for consumers.
The command constructors already take a `*props.Props`-shaped dependency, so the
seam is clean — this mirrors the facade/re-import pattern used across the
extraction programme.

**Is this the right home to solve Ed25519/manifest once?** **Yes** — a
cross-project signing surface with three output formats and two custody models
is precisely the thing that should not live in one consumer's `internal/`.
Centralising it stops each consumer (GTB, rust-tool-base tooling, ffmpeg-wasi)
from reinventing the manifest/format glue.

**Recommendation — extract, but *sequence it after* the format decision, and do
not let it block the Rust unblock.**

1. **First**, land the **format capability** (Option A's raw-Ed25519 manifest
   sink) in the *existing* `go/signing` module and wire it through `gtb sign`.
   This is what unblocks `rtb-update`; it does not need an extraction.
2. **Then**, extract the command tree into `signctl` and re-import it into GTB,
   giving non-GTB projects a first-class `signctl` binary and a single home for
   the format matrix.

Doing the extraction *first* would gold-plate the critical path (the Rust
consumer is blocked on a *format*, not on a *CLI boundary*). Doing it *never*
leaves a growing multi-format surface stuck in one tool's `internal/`. So:
**recommend the extraction as a fast-follow, gated behind the Option-A format
work, as its own spec.** This is a **maintainer go/no-go**, not an automatic
consequence of the signing work.

## 5. Cross-repo implementation sketch (for the recommended Option A + fast-follow extraction)

Illustrative only — no code, no releases. Sequencing respects inter-module
dependencies.

1. **`gitlab.com/phpboyscout/go/signing-aws-kms`** — add the Ed25519 backend
   branch from issue #5, but treat it as a **`crypto.Signer` that returns a raw
   64-byte signature**: `newSigner` accepts the `ed25519.PublicKey` from
   `kms:GetPublicKey`; `Sign` calls `ED25519_SHA_512` + `MessageType: RAW`
   honouring the Ed25519 `crypto.Signer` contract (`opts.HashFunc() ==
   crypto.Hash(0)`); return a **typed error** if the message exceeds 4096 bytes
   rather than surfacing a raw AWS `ValidationException`. RSA path untouched.
   Correct the three stale "KMS does not expose Ed25519" comments.

2. **`gitlab.com/phpboyscout/go/signing`** — add a **raw detached-Ed25519 output
   mode** (a sink that writes the backend signer's raw 64-byte signature over
   the manifest bytes), distinct from the existing `openpgpkey` armored path.
   This is the new Rust-facing format. It deliberately does **not** go through
   go-crypto's OpenPGP signing, so the opaque-Ed25519 gap (§2.4) is not on this
   path. (If the maintainer *also* wants OpenPGP-Ed25519 for the Go path, that
   is the separate issue-#5 work and must first resolve §2.4.)

3. **`go-tool-base`** — `gtb sign` gains a `--format {openpgp|raw-ed25519}` (name
   TBD) so it can emit the raw `.sig` over `checksums.txt`; release tooling
   publishes `checksums.txt` + `checksums.txt.sig` + per-archive `.sum`. Add an
   end-to-end test that a `gtb sign`-produced raw Ed25519 manifest signature
   verifies with an `ed25519-dalek`-equivalent check. Update
   `docs/how-to/mint-signing-key.md` and the release docs for the manifest
   model.

4. **`phpboyscout/terraform-aws-signing-kms`** — allow `ECC_NIST_EDWARDS25519`
   in the `key_spec` validation; document it as the preferred spec for **new**
   keys with `RSA_4096` retained for existing ones; correct the stale rationale
   comment; confirm the OIDC signer role's `kms:Sign` grant is
   algorithm-agnostic (it is per-key, not per-algorithm).

5. **`rust-tool-base`** — recompose `rtb-update` to verify **the manifest
   signature** (its existing `ed25519()` over the manifest bytes) and then each
   archive's SHA-256 **against the manifest** (its existing `checksums()`),
   instead of a per-archive signature over the archive. Update
   `docs/how-to/secure-releases.md` producer contract accordingly. The
   `Vec<[u8;32]>` any-one rotation model is unchanged.

6. **Fast-follow (separate spec, maintainer go/no-go, §4):** extract the
   `sign`/`keys` command tree into `gitlab.com/phpboyscout/go/signctl` and
   re-import into GTB; give `ffmpeg-wasi` / rust-tool-base tooling a standalone
   `signctl` binary; make `signctl` the single home for the OpenPGP / raw-Ed25519
   / (optional) minisign format matrix.

## 6. Open questions / maintainer decisions

1. **The custody fork (the decisive call).** Adopt **Option A** (KMS custody;
   PureEd25519 over a <4 KB manifest; `rtb-update` moves its root of trust to the
   manifest) — **recommended** — or accept **Option B**'s software-key custody
   downgrade to keep per-archive whole-file signatures (and the door to
   `cargo-binstall`), or run **Option C**'s two-custody-model hybrid? This is a
   security-posture decision the maintainer owns; the recommendation is A, but
   the trade is real.

2. **Does `rtb-update` accept the manifest-contract change, and on what
   timeline?** Option A depends on a `verify.rs`/`secure-releases.md` change in
   `rust-tool-base`. If that repo cannot take it soon, fall back to Option C to
   unblock without waiting.

3. **Standalone `signctl` — go or no-go, and when?** Recommended as a
   **fast-follow** gated behind the Option-A format work (§4), as its own spec —
   not on the Rust-unblock critical path. Confirm the name (`signctl`?) and
   whether it ships a public binary for non-Go pipelines.

4. **Rotation timing against the in-flight rekey.** A rotation is live
   (`2026-07-24-prod-rebuild-and-rekey`: v1 abandoned in the old account, v2
   minted in prod). A key's algorithm is fixed for its lifetime, so moving a
   project to Ed25519 is itself a rotation. Do we (a) hold the Ed25519 work until
   the current overlap window closes, (b) land the non-key-touching pieces
   (`go/signing` raw sink, terraform, `rtb-update`) now and gate only the KMS
   Ed25519 **key mint** until after, or (c) fold an Ed25519 key mint into the
   current rekey? **First-key adopters are the cheapest** — a project minting its
   first key can start on Ed25519 at zero rotation cost.

5. **`cargo-binstall` — in or out of scope?** §2.3 shows it needs *prehashed*
   minisign, which conflicts with `rtb-update`'s pure-only rule and cannot come
   from KMS. Confirm it is **out of scope** for this work (recommended), or
   accept that serving it means a **separate software-minisign channel** (Option
   B territory) *and* a Rust-side change to also accept prehashed.

6. **GovCloud / China partition coverage.** AWS lists Ed25519 in all partitions,
   but the signer role, key policy, and Terraform module should be confirmed
   against whichever partitions any regulated downstream actually deploys to
   before the terraform change is called done.
