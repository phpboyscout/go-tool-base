## 1. The real problem — two consumers, both algorithms

### 1.1 What must be true

GTB (and non-GTB tools that reuse its release pattern — `ffmpeg-wasi`,
`rust-tool-base`) publish `cargo-bin`-style precompiled binary artifacts. **Two
independent Rust consumers must be able to verify each artifact:**

1. **cargo-binstall** — *install-time*. Verifies a per-artifact **minisign**
   signature using the `pubkey` pinned in the crate's
   `[package.metadata.binstall.signing]`.
2. **rtb-update** — *self-update*. Verifies a per-artifact Ed25519 detached
   signature (raw 64-byte `.sig` or minisign `.minisig`) against one of
   `ToolMetadata::update_public_keys` (`Vec<[u8; 32]>`, any-one-verifies).

Both algorithms remain supported across the signing programme — **RSA retained,
Ed25519 preferred** — and the signing tool is algorithm-agnostic. The *artifact*
path standardises on Ed25519/minisign because that is what these two consumers
speak; GTB's *own* Go self-update manifest path keeps its existing
KMS-RSA-over-OpenPGP signature unchanged.

### 1.2 Why issue #5's framing does not get there

Issue #5 proposed *"add Ed25519 to the existing OpenPGP+KMS backend."* That is
useful housekeeping for GTB's **own** OpenPGP self-update path, but it does not
serve either Rust consumer, for two structural reasons developed in §2:

- **Container.** Neither consumer parses OpenPGP. cargo-binstall speaks
  minisign; rtb-update speaks raw-Ed25519 / minisign. An OpenPGP-Ed25519
  signature is unreadable to both.
- **Custody physics.** KMS **cannot** produce the per-artifact signature at all
  — a KMS `Sign` call is capped at a 4096-byte message, and a release archive is
  megabytes. So the per-artifact key is *forced* to be a **software** Ed25519
  key, not an HSM key. Issue #5's "hold the artifact key in KMS" is physically
  unavailable for this path.

The problem is therefore **format + custody-model**, and it is what this spike
designs.

## 2. Ground truth (confirmed facts, with the one correction)

### 2.1 The forced-software-key finding — KMS cannot sign an artifact (CONFIRMED)

The AWS KMS `Sign` API caps the message at 4096 bytes. Verbatim, from the API
reference:

> **Message** — Specifies the message or message digest to sign. **Messages can
> be 0-4096 bytes. To sign a larger message, provide a message digest.** … Type:
> Base64-encoded binary data object. **Length Constraints: Minimum length of 1.
> Maximum length of 4096.**

and, for the Edwards curve specifically:

> ED25519_SHA_512 signing algorithm requires AWS KMS `MessageType:RAW` …
> ED25519_PH_SHA_512 signing algorithm requires AWS KMS `MessageType:DIGEST`.
> When you specify the ED25519_PH_SHA_512 signing algorithm with
> `MessageType:DIGEST`, AWS KMS still performs the SHA-512 prehash … the input
> is hashed twice.

The consequence is decisive:

- **PureEd25519** over an artifact (`ED25519_SHA_512` / `RAW`) is impossible —
  the artifact is far larger than 4096 bytes. This is a *pure minisign / raw-sig
  over the whole file* — exactly what both consumers verify — and KMS cannot
  produce it.
- **`ED25519_PH_SHA_512` is not an escape hatch.** It is a *different algorithm*
  (Ed25519ph / HashEdDSA, over a **SHA-512** prehash) and its output is not the
  signature minisign or `ed25519-dalek`'s pure `verify()` checks. minisign's own
  prehash is **BLAKE2b-512**, which KMS does not offer at all.

> **Therefore the per-artifact leaf signing key MUST be a software Ed25519 key.**
> HSM-per-signature is unavailable for the artifact path. KMS remains the custody
> anchor only for GTB's own **≤ 4 KB checksums manifest** (which fits the cap),
> and for *attesting* the software leaf key (§3.4).

References:
:   KMS `Sign` API (<https://docs.aws.amazon.com/kms/latest/APIReference/API_Sign.html>),
    KMS key-spec reference
    (<https://docs.aws.amazon.com/kms/latest/developerguide/symm-asymm-choose-key-spec.html>),
    Edwards-curve GA
    (<https://aws.amazon.com/about-aws/whats-new/2025/11/aws-kms-edwards-curve-digital-signature-algorithm/>).

### 2.2 The two consumers want *opposite* minisign variants (CONFIRMED — this inverts the assumption)

minisign has two on-wire variants, distinguished by a 2-byte algorithm tag:

| Tag | Name | What is signed |
|-----|------|----------------|
| `Ed` (`0x45 0x64`) | **legacy / pure** | `ed25519(<file bytes>)` |
| `ED` (`0x45 0x44`) | **prehashed** (minisign's modern default) | `ed25519(BLAKE2b-512(<file bytes>))` |

- **rtb-update requires PURE `Ed` and rejects prehashed `ED`.** From
  `crates/rtb-update/src/verify.rs`: `if decoded[0..2] != *b"Ed" { return None }`
  — the "ED" (prehashed BLAKE2b) variant is rejected with a clear error.
- **cargo-binstall requires PREHASHED `ED` and rejects pure `Ed`.** Its
  `SIGNING.md` states verbatim *"The legacy signature format is not supported."*
  It verifies through the `minisign-verify` crate, whose `verify(..., allow_legacy)`
  returns `Error::UnexpectedAlgorithm` for a legacy `Ed` signature when
  `allow_legacy` is false — and cargo-binstall does not allow legacy. Prehashed
  is also minisign's default (`minisign -S` with no legacy flag emits `ED`).

> **Correction to the working assumption.** The plan-of-record assumed *pin to
> pure "Ed", because cargo-binstall's default prehashed "ED" is the trap.* The
> confirmed facts are the **inverse**: **cargo-binstall requires prehashed
> `ED`**; it is **rtb-update** that is the outlier by requiring pure `Ed`. A
> single **pure** signature therefore **cannot** serve both consumers. The
> unification must standardise on **prehashed `ED`** and bring rtb-update to it
> (§3).

References:
:   cargo-binstall `SIGNING.md`
    (<https://github.com/cargo-bins/cargo-binstall/blob/main/SIGNING.md>),
    `minisign-verify` crate `allow_legacy` behaviour
    (<https://docs.rs/minisign-verify/>),
    minisign format (<https://jedisct1.github.io/minisign/>),
    rtb-update `verify.rs` (read from source).

### 2.3 Container + naming facts (CONFIRMED)

- GTB's signing stack emits **ASCII-armored OpenPGP** (`go/signing/openpgpkey`
  → `openpgp.DetachSign` → `armor.Encode`). Neither Rust consumer parses OpenPGP
  — confirming §1.2's container mismatch for the artifact path.
- rtb-update selects format by **extension**: `.minisig` → minisign parse; any
  other name → raw 64-byte. So a minisign-format body **must** be named
  `.minisig` for rtb-update; a `.sig` must be exactly 64 raw bytes. rtb-update's
  asset resolver **prefers `.minisig`**. cargo-binstall's signature URL is
  configurable via the `file` template. → publishing a single `<artifact>.minisig`
  and pointing cargo-binstall's `file` at it lets **one file** serve both.
- minisign `.minisig` carries a **trusted comment** and a **global signature**
  `ed25519(<signature> || <trusted comment>)` — a *second* signature needing the
  key again. A **software** key produces this natively in one `minisign -S`;
  rtb-update ignores the trusted comment, cargo-binstall/minisign-verify checks
  it. Both are satisfied by a normally-produced `.minisig`.

### 2.4 The go-crypto opaque-signer gap (CONFIRMED — now off the critical path)

go-crypto v1.4.1's OpenPGP Ed25519 signing branch hard-asserts a concrete
`*ed25519.PrivateKey` (no `crypto.Signer` fall-through), so an opaque KMS signer
cannot drive OpenPGP-Ed25519. This *would* block issue #5's OpenPGP-Ed25519
idea, but the corrected design does **not** put Ed25519 through OpenPGP — the
artifact path is software-minisign, and KMS keeps signing GTB's manifest with
**RSA** (unaffected). So this gap is documented but no longer on the critical
path.

## 3. The unified design — one signature, one software key, both consumers

### 3.1 One signature file per artifact

For every published artifact, emit a **single prehashed (`ED`) minisign
signature**, named `<artifact>.minisig`, produced from **one software Ed25519
key**:

```
minisign -S -s <leaf.key> -m <artifact> -x <artifact>.minisig      # prehashed "ED" (default)
```

- **cargo-binstall** verifies it natively: `algorithm = "minisign"`,
  `pubkey = <leaf pubkey>`, `file = "…/<artifact>.minisig"`.
- **rtb-update** verifies the *same file* once its verifier accepts prehashed
  `ED` (§3.3) and pins the same leaf key in `update_public_keys`.

One key, one signature file, both consumers. (RSA and OpenPGP remain available
in the tool for GTB's own Go self-update manifest and any OpenPGP-native
consumer — §3.5.)

### 3.2 Why prehashed `ED`, not pure `Ed`

Prehashed is the only variant that can be **shared**: cargo-binstall rejects
pure (§2.2), so pure cannot serve it; prehashed is cargo-binstall's requirement,
minisign's modern default, and its recommended future (minisign is deprecating
legacy). Bringing rtb-update to prehashed aligns everything forward. The
alternative — publishing *two* signature files (a pure `Ed` for rtb-update and a
prehashed `ED` for cargo-binstall) from the same key — is the fallback if the
maintainer declines any rtb-update crypto change (§3.3, §6 D-2).

### 3.3 The rtb-update change (small, well-scoped)

rtb-update already parses minisign and extracts the 64-byte signature; today it
verifies `vk.verify(asset_bytes, &sig)` (pure) and rejects the `ED` tag. To
accept the shared prehashed signature it must:

- accept the `ED` (`0x45 0x44`) algorithm tag, and
- verify `vk.verify(BLAKE2b-512(asset_bytes), &sig)` for prehashed inputs (add a
  `blake2` dependency).

Recommended: **accept both** `Ed` (existing) and `ED` (new), so already-published
pure signatures keep verifying while new releases use the shared `ED`. This
answers the "does rtb-update still need a manifest path?" question (§6 D-3):
**no manifest path is needed for the artifact** — per-artifact prehashed minisign
fully covers rtb-update once it accepts `ED`. rtb-update keeps its independent
SHA-256 `.sum` check as defence-in-depth if desired, but the signature no longer
needs a manifest indirection.

### 3.4 Leaf-key custody — offline-root / online-leaf

Because the leaf is forced to be software (§2.1), custody is rooted by
**attestation**, not by holding the leaf in an HSM:

- **Leaf (online):** a software Ed25519 minisign key, present in CI at signing
  time. Short-lived / OIDC-fetched from a secrets manager, scoped to a protected
  release pipeline, rotated on a schedule. Its **public** half is what both
  consumers pin (cargo-binstall `pubkey`, rtb-update `update_public_keys`).
- **Root (offline / HSM):** the leaf public key is **certified** by a
  higher-trust key held with full custody — either the **KMS** anchor or the
  existing **offline rotation-authority** key (already Ed25519 per issue #5).
  This produces an auditable provenance record and a controlled rotation
  mechanism (root signs each new leaf; the any-one-verifies key sets rotate).
- **GTB's own manifest path is unchanged:** KMS continues to sign GTB's Go
  self-update `checksums.txt` (RSA today) over OpenPGP — that message is ≤ 4 KB
  and stays fully HSM-custodied.

**Honesty note for ratification (§6 D-1):** neither cargo-binstall nor rtb-update
*verifies the root attestation on the wire* — both pin the **leaf** public key
directly. The offline-root therefore buys **provenance, rotation control, and
auditability**, not an extra runtime signature check at the consumer. The leaf
key is genuinely exposed in CI; the root-attestation limits blast radius
(rotate-and-re-attest) but does not make the leaf HSM-custodied. This trade —
software leaf, HSM/offline-attested — is the maintainer's to ratify.

### 3.5 Algorithm-agnostic, both algorithms retained

The signing tool supports **both RSA and Ed25519** across its backends; Ed25519
is preferred for new keys, RSA retained for existing ones. The artifact path
uses software-Ed25519/minisign; the manifest path uses KMS-RSA/OpenPGP; nothing
forces existing RSA keys or in-field binaries to move.

## 4. Standalone `signctl` — extract first

**Decision context:** the maintainer elevated the extraction from fast-follow to
**do-first**. Signing is now cross-project (GTB, rust-tool-base, ffmpeg-wasi) and
the format surface is genuinely a matrix — `{KMS, software} × {RSA, Ed25519} ×
{OpenPGP, minisign-prehashed, raw-64-byte}`. That surface should not live inside
one consumer's `internal/`.

**What exists / what extracts.** The two *libraries* are already published
modules: `go/signing` (`openpgpkey` + `verify`, pinned `v0.2.2`) and
`go/signing-aws-kms` (KMS `crypto.Signer` backend, `v0.2.5`). What is *not*
importable is the **command tree** — `internal/cmd/sign/` and
`internal/cmd/keys/` (`sign`, `keys mint|generate|wkd`) — locked in GTB's
`internal/`. Extract it into a new standalone module, provisionally
`gitlab.com/phpboyscout/go/signctl` (name TBD, §6 D-4), that:

- wraps the existing `go/signing` + `go/signing-aws-kms` libraries (no library
  re-extraction);
- ships a **standalone binary** (`go install …/signctl@latest`) so non-Go /
  non-GTB release pipelines (rust-tool-base, ffmpeg-wasi) sign without a GTB
  build;
- is the single **home for the format matrix** — and specifically the home where
  the new **software-Ed25519 prehashed-minisign** artifact-signing capability
  (§3) lands, alongside the existing KMS-RSA-OpenPGP manifest path;
- exposes `sign` / `keys` as Cobra command constructors so **GTB re-imports** it
  and `gtb sign` / `gtb keys` keep working unchanged (the constructors already
  take a `*props.Props`-shaped dependency — the seam mirrors every other
  extracted module's facade).

**Extraction order (extract-first):**

1. Extract the command tree into `signctl`, wrapping the two libraries; GTB
   re-imports; `gtb sign`/`gtb keys` unchanged (pure move — no behaviour change).
2. **Inside `signctl`,** add the software-Ed25519 prehashed-minisign artifact
   sink (§3) and the KMS-Ed25519 branch for the manifest path where wanted.
3. Publish `signctl` binary for the non-Go consumers.

The Ed25519/minisign artifact work is thus done **once, in `signctl`**, not
re-implemented per consumer.

## 5. Cross-repo implementation sketch

Illustrative only — no code, no releases. KMS-key-touching steps are gated (§6
D-5).

1. **`gitlab.com/phpboyscout/go/signctl` (NEW — extract first).** Move
   `internal/cmd/sign` + `internal/cmd/keys` out of GTB into a standalone module
   wrapping `go/signing` + `go/signing-aws-kms`; expose command constructors +
   a standalone binary. Home for the format matrix.

2. **`gitlab.com/phpboyscout/go/signing`.** Add a **software-Ed25519
   prehashed-minisign** output capability (produce a proper `.minisig`: `ED`
   tag, BLAKE2b-512 prehash, trusted comment + global signature) — via a
   vetted Go minisign library or a controlled `minisign` invocation — plus a
   **raw-64-byte** sink. Keep the OpenPGP path for GTB's manifest. Not on the
   go-crypto opaque-Ed25519 path (§2.4).

3. **`gitlab.com/phpboyscout/go/signing-aws-kms`.** Add the additive Ed25519
   branch (accept `ECC_NIST_EDWARDS25519`; `ED25519_SHA_512`/`RAW`; typed error
   above 4096 bytes) **for the ≤ 4 KB manifest / leaf-attestation use only**;
   RSA retained; correct the three stale "KMS does not expose Ed25519" comments.
   *(KMS-key-touching → gated.)*

4. **`rust-tool-base` / `rtb-update`.** Accept the prehashed `ED` minisign
   variant (add BLAKE2b-512; keep pure `Ed` for back-compat); pin the shared
   leaf key in `update_public_keys`; drop the per-artifact manifest requirement
   (per-artifact minisign covers it). Update `docs/how-to/secure-releases.md`
   producer contract from "Ed25519 signature over the archive" to "prehashed
   minisign `.minisig` over the archive."

5. **`phpboyscout/terraform-aws-signing-kms`.** Allow `ECC_NIST_EDWARDS25519` in
   `key_spec`; document Ed25519 as preferred for new keys, RSA_4096 retained;
   provision the **leaf-attestation root** key (KMS or offline-authority) if the
   maintainer roots via KMS. *(KMS-key-touching → gated.)*

6. **`go-tool-base`.** Re-import `signctl` (`gtb sign`/`gtb keys` unchanged);
   configure release tooling to emit `<artifact>.minisig` per artifact + keep
   the KMS-RSA OpenPGP manifest for Go self-update; add an end-to-end test that a
   published `.minisig` verifies under both an `ed25519-dalek`-equivalent
   (prehashed) check and a `minisign-verify` (`allow_legacy=false`) check; add
   the `[package.metadata.binstall.signing]` example (`file → .minisig`) to docs;
   update `docs/how-to/mint-signing-key.md`.

## 6. Maintainer decisions

- **D-1 — Leaf-key custody ratification (decisive).** Accept the forced model:
  **software Ed25519 leaf key in CI, HSM/offline-authority *attested*** (§3.4).
  Confirm the root of attestation — **KMS** or the **offline rotation-authority**
  key — and accept, eyes-open, that consumers pin the *leaf* (the root buys
  provenance/rotation/audit, not a runtime check, and the leaf is genuinely
  CI-exposed). This is the security-posture call the whole artifact path rests
  on.

- **D-2 — Ratify the pure→prehashed inversion (§2.2).** The confirmed facts flip
  the assumption: standardise the shared signature on **prehashed `ED`** and
  bring **rtb-update** to accept it. Approve that, or choose the fallback —
  publish **two** signature files per artifact (pure `Ed` + prehashed `ED`) from
  one key, avoiding any rtb-update crypto change at the cost of a second artifact
  and a split contract.

- **D-3 — rtb-update scope.** Confirm rtb-update accepts prehashed `ED` (recommend
  *accept both* for back-compat) and **drops the manifest path** for artifacts
  (per-artifact minisign fully covers it); decide whether to keep the SHA-256
  `.sum` as defence-in-depth.

- **D-4 — `signctl` name + surface.** Ratify **extract-first**; confirm the module
  name (`signctl`?) and that it ships a public binary for non-Go pipelines.

- **D-5 — Rotation gating (HELD).** The `2026-07-24-prod-rebuild-and-rekey` is
  **not complete** (spec still `approved`, dual-sign window open; maintainer
  finishes it Friday). **Hold all KMS-key-touching work** — new key mint,
  terraform apply, attestation-root provisioning — until after. Non-key-touching
  work can be spec'd/started now: the `signctl` extraction, the software-minisign
  output format in `go/signing`, and the rtb-update verify change. First-ever
  keys are the cheapest Ed25519 adopters (zero rotation cost).

- **D-6 — RSA/Ed25519 default.** Ed25519 preferred for new keys, RSA retained;
  confirm whether tooling *defaults* new projects to Ed25519 once this lands or
  keeps RSA_4096 default through a bake-in period.
