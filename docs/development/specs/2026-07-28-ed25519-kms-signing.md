## 1. The real problem — two consumers, both algorithms

### 1.1 What must be true

GTB (and non-GTB tools that reuse its release pattern — `ffmpeg-wasi`,
`rust-tool-base`) publish `cargo-bin`-style precompiled binary artifacts. **Two
independent Rust consumers must be able to verify each artifact:**

1. **cargo-binstall** — *install-time*. Verifies a per-artifact **minisign**
   signature using the `pubkey` pinned in the crate's
   `[package.metadata.binstall.signing]`.
2. **rtb-update** — *self-update*. Verifies a per-artifact Ed25519 detached
   signature (raw 64-byte `.sig` or minisign `.minisig`) against one of
   `ToolMetadata::update_public_keys` (`Vec<[u8; 32]>`, any-one-verifies).

Both algorithms remain supported across the signing programme — **RSA retained,
Ed25519 preferred** — and the signing tool is algorithm-agnostic. The *artifact*
path standardises on Ed25519/minisign because that is what these two consumers
speak; GTB's *own* Go self-update manifest path keeps its existing
KMS-RSA-over-OpenPGP signature unchanged.

### 1.2 Why issue #5's framing does not get there

Issue #5 proposed *"add Ed25519 to the existing OpenPGP+KMS backend"* and sign
`checksums.txt`. That is useful housekeeping for GTB's **own** OpenPGP
self-update path, but it does not serve either Rust consumer:

- **Wrong container.** Neither consumer parses OpenPGP. cargo-binstall speaks
  **minisign**; rtb-update speaks **raw-Ed25519 / minisign**. An OpenPGP-Ed25519
  signature is unreadable to both. The fix is a **minisign** signature, not an
  Ed25519 signature wrapped in OpenPGP.
- **Wrong granularity.** Both consumers verify a **per-artifact** signature over
  the archive; issue #5 signs a single `checksums.txt` manifest.

What issue #5 got *right* and this spike keeps: the signing key can stay
**KMS-held with full HSM custody**. The earlier draft of this spike wrongly
concluded that KMS *cannot* produce the per-artifact signature and that the key
was therefore forced to be software. §2 corrects that — the minisign prehashed
variant is specifically what makes a KMS-held key work.

The problem is therefore **container + granularity**, solved by a KMS-held
Ed25519 key producing a per-artifact minisign signature (§3).

## 2. Ground truth (confirmed facts)

### 2.1 The KMS 4096-byte cap — real, but it does NOT force a software key (CORRECTED)

The AWS KMS `Sign` API caps the message at 4096 bytes. Verbatim, from the API
reference:

> **Message** — Specifies the message or message digest to sign. **Messages can
> be 0-4096 bytes. To sign a larger message, provide a message digest.** … Type:
> Base64-encoded binary data object. **Length Constraints: Minimum length of 1.
> Maximum length of 4096.**

and, for the Edwards curve:

> ED25519_SHA_512 signing algorithm requires AWS KMS `MessageType:RAW` …
> ED25519_PH_SHA_512 signing algorithm requires AWS KMS `MessageType:DIGEST`.
> When you specify the ED25519_PH_SHA_512 signing algorithm with
> `MessageType:DIGEST`, AWS KMS still performs the SHA-512 prehash … the input
> is hashed twice.

**What is genuinely impossible:** signing the *raw multi-MB artifact* as the KMS
message — that exceeds 4096 bytes. So minisign's **legacy / pure** variant,
which is `ed25519(<whole file data>)`, cannot be produced by KMS for a real
archive. That much of the earlier draft was correct.

**The correction — the prehashed variant sidesteps the cap.** Per the
authoritative minisign specification, the two variants are:

> `signature (legacy): ed25519(<file data>)` — algorithm tag **`Ed`**
> `signature (prehashed): ed25519(Blake2b-512(<file data>))` — algorithm tag **`ED`**

The prehashed **`ED`** signature is **ordinary Ed25519 applied to the 64-byte
BLAKE2b-512 digest of the file** — the digest is computed *outside* the signer
and handed to a standard Ed25519 signing operation as its message. It is **not**
Ed25519ph / HashEdDSA (the minisign spec references no such thing; it is a plain
hash-then-sign). Therefore:

- You compute `d = BLAKE2b-512(artifact)` yourself — **64 bytes**.
- You call `kms:Sign(Message = d, MessageType = RAW, SigningAlgorithm =
  ED25519_SHA_512)`. 64 bytes is trivially under the 4096-byte cap, and RAW mode
  is exactly *standard* Ed25519 over the supplied message — precisely what
  minisign's `ED` variant needs.
- KMS returns the 64-byte Ed25519 signature, which **is** minisign's `<signature>`
  field for the `ED` variant.

> **Corrected conclusion:** a **KMS-held Ed25519 key CAN produce a complete
> minisign `ED` signature**. The BLAKE2b-512 prehash is exactly what makes it
> KMS-compatible (it collapses an arbitrarily large file to a 64-byte message).
> The per-artifact key is **not** forced to be software; **full HSM custody is
> preserved** (§3). `ED25519_PH_SHA_512` is *still* the wrong algorithm — we do
> **not** use it (it is Ed25519ph over a SHA-512 prehash, and KMS re-hashes) —
> we use `ED25519_SHA_512`/`RAW` over the externally-computed BLAKE2b digest.

:   KMS `Sign` API (<https://docs.aws.amazon.com/kms/latest/APIReference/API_Sign.html>),
    KMS key-spec reference
    (<https://docs.aws.amazon.com/kms/latest/developerguide/symm-asymm-choose-key-spec.html>),
    Edwards-curve GA
    (<https://aws.amazon.com/about-aws/whats-new/2025/11/aws-kms-edwards-curve-digital-signature-algorithm/>),
    minisign format spec (<https://jedisct1.github.io/minisign/>).

### 2.2 The two consumers want *opposite* minisign variants (CONFIRMED)

minisign has two on-wire variants, distinguished by a 2-byte algorithm tag:

| Tag | Name | What is signed | KMS-signable? |
|-----|------|----------------|---------------|
| `Ed` (`0x45 0x64`) | **legacy / pure** | `ed25519(<file bytes>)` | **No** — whole file > 4096 B |
| `ED` (`0x45 0x44`) | **prehashed** (minisign's modern default) | `ed25519(BLAKE2b-512(<file bytes>))` | **Yes** — 64-byte digest |

- **cargo-binstall requires PREHASHED `ED` and rejects pure `Ed`.** Its
  `SIGNING.md` states verbatim *"The legacy signature format is not supported."*
  It verifies through the `minisign-verify` crate, whose `verify(..., allow_legacy)`
  returns `Error::UnexpectedAlgorithm` for a legacy `Ed` signature when
  `allow_legacy` is false — and cargo-binstall does not allow legacy. Prehashed
  is also minisign's default (`minisign -S` with no legacy flag emits `ED`).
- **rtb-update requires PURE `Ed` and rejects prehashed `ED`** *today*. From
  `crates/rtb-update/src/verify.rs`: `if decoded[0..2] != *b"Ed" { return None }`.

**This is doubly fortunate.** cargo-binstall requires the **`ED`** variant, which
is exactly the **KMS-signable** one. So serving cargo-binstall does *not* force a
software key — it points us at the variant that preserves HSM custody. A single
**`ED`** signature serves both consumers once rtb-update is taught to accept `ED`
(§3.3). (A single *pure* signature could not have served both — cargo-binstall
rejects pure — so standardising on `ED` is both the KMS-custody choice and the
only shareable choice.)

References:
:   cargo-binstall `SIGNING.md`
    (<https://github.com/cargo-bins/cargo-binstall/blob/main/SIGNING.md>),
    `minisign-verify` crate `allow_legacy` behaviour
    (<https://docs.rs/minisign-verify/>),
    minisign format (<https://jedisct1.github.io/minisign/>),
    rtb-update `verify.rs` (read from source).

### 2.3 Container, naming, and the global signature (CONFIRMED)

- GTB's signing stack emits **ASCII-armored OpenPGP** (`go/signing/openpgpkey`
  → `openpgp.DetachSign` → `armor.Encode`). Neither Rust consumer parses OpenPGP
  — confirming §1.2's container point. The artifact path must emit a **minisign**
  file assembled directly from the raw KMS signature, *not* via OpenPGP.
- rtb-update selects format by **extension**: `.minisig` → minisign parse; any
  other name → raw 64-byte. So a minisign body **must** be named `.minisig` for
  rtb-update; a `.sig` must be exactly 64 raw bytes. rtb-update's asset resolver
  **prefers `.minisig`**. cargo-binstall's signature URL is configurable via the
  `file` template → publishing a single `<artifact>.minisig` and pointing
  cargo-binstall's `file` at it lets **one file** serve both.
- The minisign file carries a **trusted comment** and a **global signature**
  `global_signature = ed25519(<signature> || <trusted_comment>)` — a *second*
  Ed25519 signature. Its message is `64-byte signature || short comment`, again
  well under the 4096-byte cap, so it is **also a KMS `ED25519_SHA_512`/`RAW`
  call** (§3.2). rtb-update ignores the trusted comment; cargo-binstall /
  minisign-verify checks the global signature — both are satisfied by a properly
  assembled `.minisig`.

### 2.4 The go-crypto opaque-signer gap (CONFIRMED — off the critical path)

go-crypto v1.4.1's OpenPGP Ed25519 signing branch hard-asserts a concrete
`*ed25519.PrivateKey` (no `crypto.Signer` fall-through), so an opaque KMS signer
cannot drive OpenPGP-Ed25519. This would block issue #5's OpenPGP-Ed25519 idea,
but the corrected design does **not** route the artifact signature through
OpenPGP — it assembles the minisign container **ourselves** from the raw KMS
Ed25519 signature. So the gap is documented but bypassed. (GTB's own manifest
path keeps signing with **RSA** over OpenPGP, which is unaffected.)

## 3. The unified design — one KMS-held key, one per-artifact signature, both consumers

### 3.1 Custody: a KMS-held Ed25519 key (full HSM custody, no software key)

The per-artifact signing key is a **KMS-held Ed25519 key**
(`ECC_NIST_EDWARDS25519`), with the **same custody model as the existing KMS-held
RSA key**: the private half never leaves the HSM boundary, the signer role is
OIDC-assumed, and the key policy is the single grant surface. There is **no
software leaf key**, **no offline attestation-root**, and **no custody
downgrade** — those were artefacts of the earlier draft's mistaken "KMS can't
sign it" premise, now removed.

### 3.2 How a per-artifact `.minisig` is produced from the KMS key

For each artifact, the signing tool (§4) performs:

1. `d = BLAKE2b-512(artifact)` — 64 bytes, computed locally (outside KMS).
2. `S = kms:Sign(Message = d, MessageType = RAW, SigningAlgorithm =
   ED25519_SHA_512)` — the 64-byte Ed25519 signature. *(KMS call #1.)*
3. Build the trusted comment (e.g. filename, version, timestamp).
4. `G = kms:Sign(Message = S ‖ trusted_comment, MessageType = RAW,
   SigningAlgorithm = ED25519_SHA_512)` — the global signature. *(KMS call #2.)*
5. Assemble `<artifact>.minisig`:
   ```
   untrusted comment: <text>
   base64( "ED" ‖ key_id ‖ S )
   trusted comment: <trusted_comment>
   base64( G )
   ```

Two KMS `Sign` calls per artifact, both RAW/`ED25519_SHA_512`, both on tiny
messages. The private key never materialises.

### 3.3 Both consumers verify the one file

- **cargo-binstall** verifies it natively: `algorithm = "minisign"`,
  `pubkey = <KMS-key public half, minisign-encoded>`,
  `file = "…/<artifact>.minisig"`. It requires `ED`, which this is.
- **rtb-update** verifies the *same file* once its verifier accepts `ED`: parse
  the 64-byte signature, compute `BLAKE2b-512(artifact)`, then
  `vk.verify(digest, &sig)`. Recommended: **accept both** `Ed` (existing) and
  `ED` (new) so already-published pure signatures keep verifying. This is a
  small, well-scoped change (accept the `ED` tag; add a `blake2` dependency).

Because the per-artifact `ED` minisign now carries the full signature, rtb-update
needs **no manifest path** for artifacts (§6 D-3); it may keep its independent
SHA-256 `.sum` check as defence-in-depth if desired.

### 3.4 Algorithm-agnostic, both algorithms retained

The signing tool supports **both RSA and Ed25519** across its backends; Ed25519
is preferred for new keys, RSA retained for existing ones. The artifact path uses
a **KMS Ed25519** key emitting minisign `ED`; GTB's own Go self-update manifest
path uses the **KMS RSA** key over OpenPGP, unchanged; nothing forces existing
RSA keys or in-field binaries to move.

### 3.5 Two implementation-detail flags to confirm during build

1. **KMS Ed25519 signature encoding.** Confirm `kms:Sign` returns the Ed25519
   signature as the **raw 64 bytes** (`R ‖ S`) that minisign and `ed25519-dalek`
   expect, **not** a DER-wrapped object. (The AWS `Sign` docs specify DER
   encoding only for the ECDSA algorithms; Ed25519 signatures are natively 64
   bytes — but verify empirically, since a DER wrapper would break both
   consumers.)
2. **Two KMS `Sign` calls per artifact.** The main signature and the global
   signature are separate KMS calls (§3.2). Account for this in KMS request
   quotas / cost and in the release pipeline's retry/timeout budget when signing
   a large target matrix.

## 4. Standalone `signctl` — extract first

**Decision context:** the maintainer elevated the extraction from fast-follow to
**do-first**. Signing is now cross-project (GTB, rust-tool-base, ffmpeg-wasi) and
the format surface is genuinely a matrix — `{KMS, software} × {RSA, Ed25519} ×
{OpenPGP, minisign-prehashed, raw-64-byte}`. That surface should not live inside
one consumer's `internal/`.

**What exists / what extracts.** The two *libraries* are already published
modules: `go/signing` (`openpgpkey` + `verify`, pinned `v0.2.2`) and
`go/signing-aws-kms` (KMS `crypto.Signer` backend, `v0.2.5`). What is *not*
importable is the **command tree** — `internal/cmd/sign/` and
`internal/cmd/keys/` (`sign`, `keys mint|generate|wkd`) — locked in GTB's
`internal/`. Extract it into a new standalone module, provisionally
`gitlab.com/phpboyscout/go/signctl` (name TBD, §6 D-4), that:

- wraps the existing `go/signing` + `go/signing-aws-kms` libraries (no library
  re-extraction);
- ships a **standalone binary** (`go install …/signctl@latest`) so non-Go /
  non-GTB release pipelines (rust-tool-base, ffmpeg-wasi) sign without a GTB
  build;
- is the single **home for the format matrix** — and specifically where the new
  **KMS-Ed25519 → prehashed-minisign** artifact-signing capability (§3) lands,
  alongside the existing KMS-RSA-OpenPGP manifest path;
- exposes `sign` / `keys` as Cobra command constructors so **GTB re-imports** it
  and `gtb sign` / `gtb keys` keep working unchanged (the constructors already
  take a `*props.Props`-shaped dependency — the seam mirrors every other
  extracted module's facade).

**Extraction order (extract-first):**

1. Extract the command tree into `signctl`, wrapping the two libraries; GTB
   re-imports; `gtb sign`/`gtb keys` unchanged (pure move — no behaviour change).
2. **Inside `signctl`,** add the KMS-Ed25519 → prehashed-minisign artifact sink
   (§3): BLAKE2b-512 the file, KMS RAW-sign the digest and the global signature,
   assemble the `.minisig`.
3. Publish the `signctl` binary for the non-Go consumers.

The Ed25519/minisign artifact work is thus done **once, in `signctl`**, not
re-implemented per consumer.

## 5. Cross-repo implementation sketch

Illustrative only — no code, no releases. KMS-key-touching steps are gated (§6
D-5).

1. **`gitlab.com/phpboyscout/go/signctl` (NEW — extract first).** Move
   `internal/cmd/sign` + `internal/cmd/keys` out of GTB into a standalone module
   wrapping `go/signing` + `go/signing-aws-kms`; expose command constructors + a
   standalone binary. Home for the format matrix; host of the new minisign sink.

2. **`gitlab.com/phpboyscout/go/signing`.** Add a **KMS-Ed25519 →
   prehashed-minisign** assembler: BLAKE2b-512 the file, drive the KMS
   `crypto.Signer` for the 64-byte main signature and the global signature, emit
   a spec-correct `ED` `.minisig` (plus a raw-64-byte sink for the `.sig` form).
   Assembled directly from the raw KMS signature — **not** via go-crypto OpenPGP
   (§2.4). Keep the OpenPGP path for GTB's manifest.

3. **`gitlab.com/phpboyscout/go/signing-aws-kms`.** Add the additive Ed25519
   branch (accept `ECC_NIST_EDWARDS25519`; sign via `ED25519_SHA_512`/`RAW`;
   typed error above 4096 bytes; confirm raw-64-byte signature output per §3.5).
   RSA retained; correct the three stale "KMS does not expose Ed25519" comments.
   *(KMS-key-touching → gated.)*

4. **`rust-tool-base` / `rtb-update`.** Accept the prehashed `ED` minisign variant
   (compute BLAKE2b-512 before Ed25519 verify; add `blake2`; keep pure `Ed` for
   back-compat); pin the KMS Ed25519 public half in `update_public_keys`; drop
   the per-artifact manifest requirement. Update `docs/how-to/secure-releases.md`
   from "Ed25519 signature over the archive" to "prehashed minisign `.minisig`
   over the archive."

5. **`phpboyscout/terraform-aws-signing-kms`.** Allow `ECC_NIST_EDWARDS25519` in
   `key_spec`; document Ed25519 as preferred for new keys, RSA_4096 retained;
   provision the **artifact-signing KMS Ed25519 key** and confirm the OIDC signer
   role's `kms:Sign` grant is algorithm-agnostic. No attestation-root key is
   needed (the leaf is the KMS key). *(KMS-key-touching → gated.)*

6. **`go-tool-base`.** Re-import `signctl` (`gtb sign`/`gtb keys` unchanged);
   configure release tooling to emit `<artifact>.minisig` per artifact + keep the
   KMS-RSA OpenPGP manifest for Go self-update; add an end-to-end test that a
   published `.minisig` verifies under both an `ed25519-dalek`-equivalent
   (prehashed BLAKE2b-512) check and a `minisign-verify` (`allow_legacy=false`)
   check; add the `[package.metadata.binstall.signing]` example (`file → .minisig`)
   to docs; update `docs/how-to/mint-signing-key.md`.

## 6. Maintainer decisions

- **D-1 — Artifact-signing key (custody now simple).** The artifact key is a
  **KMS-held Ed25519 key** with the *same* full-HSM custody as the existing
  KMS-held RSA key — no software leaf, no attestation-root (the earlier
  "software-leaf custody" decision is **moot** and removed). The only call is to
  **ratify minting a new KMS Ed25519 key** for the artifact path (gated behind
  the rekey, D-5), and to confirm §3.5 flag (1) — that KMS returns raw 64-byte
  Ed25519 signatures — during implementation.

- **D-2 — Standardise on prehashed `ED`.** Confirmed correct on two counts: it is
  cargo-binstall's required variant **and** the only KMS-signable one.
  Standardise the shared per-artifact signature on `ED` and bring **rtb-update**
  to accept it. (Fallback, only if rtb-update must stay pure-only: publish *two*
  files per artifact — a pure `Ed` and a prehashed `ED` — but note KMS can only
  produce the `ED` one, so the pure file would need a separate software signer;
  the shared-`ED` path avoids that entirely and is strongly preferred.)

- **D-3 — rtb-update scope.** Confirm rtb-update accepts prehashed `ED` (recommend
  *accept both* for back-compat) and **drops the manifest path** for artifacts
  (per-artifact minisign fully covers it); decide whether to keep the SHA-256
  `.sum` as defence-in-depth.

- **D-4 — `signctl` name + surface.** Ratify **extract-first**; confirm the module
  name (`signctl`?) and that it ships a public binary for non-Go pipelines.

- **D-5 — Rotation gating (HELD).** The `2026-07-24-prod-rebuild-and-rekey` is
  **not complete** (spec still `approved`, dual-sign window open; maintainer
  finishes it Friday). **Hold all KMS-key-touching work** — the new Ed25519 key
  mint, terraform apply — until after. Non-key-touching work can start now: the
  `signctl` extraction, the minisign assembler in `go/signing`, and the
  rtb-update verify change. First-ever keys are the cheapest Ed25519 adopters
  (zero rotation cost).

- **D-6 — RSA/Ed25519 default.** Ed25519 preferred for new keys, RSA retained;
  confirm whether tooling *defaults* new projects to Ed25519 once this lands or
  keeps RSA_4096 default through a bake-in period.
