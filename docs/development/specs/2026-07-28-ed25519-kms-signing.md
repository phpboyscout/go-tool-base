## 1. Reported problem and the expired constraint

The artefact-signing stack is hard-locked to RSA-4096. Three sites state the
rationale explicitly, and all three cite the same now-obsolete fact — that AWS
KMS does not expose Ed25519 for asymmetric signing:

- `go/signing-aws-kms` `awskms.go` (the `ErrUnsupportedKMSKeyType` doc comment):
  *"AWS KMS does not expose Ed25519 for asymmetric signing, so RSA is the only
  key type this backend handles."*
- `go/signing-aws-kms` `signer.go` (the `newSigner` doc comment):
  *"Only RSA SIGN_VERIFY keys are supported — that is the AWS KMS surface for
  asymmetric signing (Ed25519 is not exposed by KMS)."*
- `terraform-aws-signing-kms` `variables.tf` (the `key_spec` variable):
  *"AWS KMS does not expose Ed25519 for asymmetric signing, so RSA_4096 is the
  secure default."*

That was true when the programme was designed. **It stopped being true in
November 2025**, when AWS KMS added Edwards-curve support:

- Key spec: `ECC_NIST_EDWARDS25519`.
- Signing algorithms: `ED25519_SHA_512` (`MessageType: RAW`) and
  `ED25519_PH_SHA_512` (`MessageType: DIGEST`).
- Availability: all commercial regions plus GovCloud and China.
- References:
  - <https://aws.amazon.com/about-aws/whats-new/2025/11/aws-kms-edwards-curve-digital-signature-algorithm/>
  - <https://docs.aws.amazon.com/kms/latest/developerguide/symm-asymm-choose-key-spec.html>

The custody guarantees are unchanged: the private half never leaves the HSM
boundary, the signer role is OIDC-assumed, and the key policy remains the single
grant surface. The only thing that changed is that the held key can now be
Ed25519 instead of RSA.

Why it is worth doing (from the issue, retained here as the motivation of
record):

- Ed25519 is the better primitive for release signing — 32-byte public keys and
  64-byte signatures versus 512-byte RSA-4096 signatures, faster verification,
  and no padding-scheme choice to get wrong (the backend already has to refuse
  PSS explicitly via `ErrPSSUnsupported` to avoid a silent scheme downgrade).
- It unblocks non-Go consumers. `rust-tool-base`'s verifier is Ed25519-only
  today (`ed25519_dalek`, 32-byte keys); with Ed25519 available in KMS it can
  adopt the ecosystem's OpenPGP container and trust model rather than fork its
  own format. `ffmpeg-wasi` already reuses `gtb sign` wholesale.
- The stale comments are themselves a liability — they will keep steering future
  design toward RSA for a reason that has expired.

## 2. Independent validation of the current constraint

Each claim below was checked against the source at `origin/main` of each
module. The constraint **is still present**.

### 2.1 The RSA-only lock in the KMS backend (present)

`go/signing-aws-kms` `signer.go` `newSigner` parses the KMS public key and then
type-switches to RSA, rejecting everything else:

```go
parsed, err := x509.ParsePKIXPublicKey(out.PublicKey)
if err != nil {
    return nil, errors.Wrap(err, "parsing KMS public-key DER")
}

rsaPub, ok := parsed.(*rsa.PublicKey)
if !ok {
    return nil, errors.Wrapf(ErrUnsupportedKMSKeyType, "KMS key is %T", parsed)
}
```

The `kmsSigner` struct holds `pub *rsa.PublicKey` (an RSA-typed field, not
`crypto.PublicKey`), and `Sign` maps only the RSASSA-PKCS1-v1_5 SHA-256/384/512
algorithms via `signingAlgorithm`, with a `MessageType: DIGEST` call. There is
no Ed25519 branch anywhere in the backend.

### 2.2 The stale rationale comments (present)

Both comments quoted in §1 exist verbatim in `awskms.go` (the
`ErrUnsupportedKMSKeyType` sentinel) and `signer.go` (the `newSigner` doc
comment). They assert the KMS limitation as current fact.

### 2.3 Verify is already Ed25519-ready (confirmed)

`go/signing` `verify/signing.go` `checkKeyStrength` already accepts Ed25519 in
both packet forms and rejects everything else by name:

```go
switch pk.PubKeyAlgo {
case packet.PubKeyAlgoEdDSA, packet.PubKeyAlgoEd25519:
    return nil
case packet.PubKeyAlgoRSA, packet.PubKeyAlgoRSASignOnly:
    // ... minRSAStrengthBits check ...
```

So the **verification** side is asymmetric-ready; the offline
`rotation-authority.asc` key is itself Ed25519 and already verifies. Only the
**production signing** path is RSA-locked. The gap is precisely the signing
(mint + detached-sign) path, not verification.

### 2.4 Empirical confirmation — a red constraint test

A red test was added on branch `test/ed25519-kms-constraint-issue5` in
`go/signing-aws-kms`
(`awskms_ed25519_constraint_test.go`,
`TestNewSigner_Ed25519Key_CurrentlyRejected_Issue5`). It marshals a real
Ed25519 key to SubjectPublicKeyInfo DER (mirroring what `kms:GetPublicKey` now
returns for an `ECC_NIST_EDWARDS25519` key), feeds it through `newSigner`, and
asserts the current rejection:

```
=== RUN   TestNewSigner_Ed25519Key_CurrentlyRejected_Issue5
--- PASS: TestNewSigner_Ed25519Key_CurrentlyRejected_Issue5 (0.00s)
PASS
ok  	gitlab.com/phpboyscout/go/signing-aws-kms
```

The test passing **is** the validation: an Ed25519 KMS key is rejected today
with `ErrUnsupportedKMSKeyType`. When the additive path lands, this test flips
to a `require.NoError` acceptance assertion — its failure will be the signal
that the feature is implemented. Note in passing: the test proves the stdlib
`x509.ParsePKIXPublicKey` **does** decode the Edwards key (it returns an
`ed25519.PublicKey`); the rejection happens purely at the backend's RSA type
switch, not at the DER parse.

## 3. Assessment of the reporter's technical claims

The reporter cited specifics. They were checked independently.

| # | Claim | Verdict | Evidence |
|---|-------|---------|----------|
| 1 | KMS added `ECC_NIST_EDWARDS25519` / `ED25519_SHA_512` (RAW) / `ED25519_PH_SHA_512` (DIGEST) in Nov 2025 | **Correct** | AWS announcement + KMS key-spec docs (§1). |
| 2 | The SPKI parse already returns the Ed25519 key; the type switch just rejects it | **Correct** | `signer.go` uses `x509.ParsePKIXPublicKey`, which returns `ed25519.PublicKey`; the red test confirms parse succeeds and rejection is at the RSA assertion. |
| 3 | `crypto.Signer` Ed25519 contract = full message, `opts.HashFunc() == crypto.Hash(0)`, matching KMS `RAW` | **Correct at the boundary, with a caveat** | This is the stdlib `crypto.Signer`/`ed25519` contract. Either way it is tiny and RAW-mode-compatible. |
| 4 | KMS caps a `RAW` message at 4096 bytes; only `checksums.txt` is signed, well under the cap; a typed error is still worthwhile | **Correct** | `gtb sign` feeds `checksums.txt` into `openpgpkey.DetachSign` (`internal/cmd/sign/sign.go`). The manifest is a few hundred bytes; and per §3 note 3 the value actually handed to KMS is the ≤ 64-byte OpenPGP digest, further under the cap. `ED25519_PH_SHA_512`/`DIGEST` remains the documented escape hatch. |
| 5 | `signing/verify` already accepts Ed25519 | **Correct** | `checkKeyStrength`, §2.3. |
| 6 | The `go/signing` work is *"likely just test coverage rather than new code"* | **Incorrect / materially understated** | See §3.1 — the signing side has explicit RSA-only locks **and** a deeper go-crypto opaque-signer gap the issue does not mention. |

### 3.1 The understated `go/signing` work (the reporter's one real miss)

The issue frames `go/signing` as *"likely just test coverage."* It is not. Two
distinct pieces of real work exist, one of them non-trivial.

**(a) Explicit RSA-only locks in `openpgpkey` (new code, straightforward).**
The mint/sign surface hard-asserts RSA in three places:

- `openpgpkey.go` `Entity` — `signer.Public().(*rsa.PublicKey)`; builds the
  packet with `packet.NewRSAPublicKey`.
- `sign.go` `DetachSign` — `signer.Public().(*rsa.PublicKey)`.
- `sign.go` `assertSignerMatchesPublicKey` — RSA-only fingerprint match.

Each rejects Ed25519 with `ErrUnsupportedKeyType` today and needs an additive
branch. The package doc also states Ed25519 is *"unreachable from outside the
go-crypto module"* because it would need go-crypto's `internal/ecc`. **That
rationale is now stale for the modern path**: go-crypto (v1.4.1) exports
`packet.NewEd25519PublicKey(creationTime, *ed25519.PublicKey)`, and that
`ed25519.PublicKey` comes from go-crypto's **non-internal**
`openpgp/ed25519` package (exported `Point []byte` field, `NewPublicKey()`
constructor). So a modern RFC 9580 Ed25519 (algorithm 27) public-key packet
**can** be assembled from a raw 32-byte KMS key without touching `internal/ecc`.
The *legacy* EdDSA form (algorithm 22, via `NewEdDSAPublicKey` + `eddsa.PublicKey`)
**does** still route through `internal/ecc` and remains unreachable — so the doc
comment needs correcting-and-scoping, not wholesale deletion. Algorithm choice
(22 vs 27) is an open question (§6).

**(b) The go-crypto opaque-signer gap (the real blocker the issue misses).**
The whole `openpgpkey` design depends on driving go-crypto's signing through an
**opaque `crypto.Signer`** — it constructs
`&packet.PrivateKey{PublicKey: ..., PrivateKey: signer}` and lets go-crypto call
`signer.Sign(...)` (so the KMS-held key signs without ever materialising). This
works for RSA because go-crypto's `Signature.Sign` has a `crypto.Signer`
fall-through for the RSA (and ECDSA) branches. **It does not for Ed25519.** In
go-crypto v1.4.1 `openpgp/packet/signature.go`:

```go
case PubKeyAlgoRSA, PubKeyAlgoRSASignOnly:
    // supports both *rsa.PrivateKey and crypto.Signer
    sigdata, err := priv.PrivateKey.(crypto.Signer).Sign(config.Random(), digest, sig.Hash)
...
case PubKeyAlgoEd25519:
    sk := priv.PrivateKey.(*ed25519.PrivateKey)   // hard type assertion — no crypto.Signer path
    signature, err := ed25519.Sign(sk, digest)
```

The Ed25519 (and EdDSA) branches type-assert go-crypto's concrete
`*ed25519.PrivateKey` — there is no `crypto.Signer` fall-through. A KMS-backed
opaque signer is **not** that concrete type, so go-crypto would fail the
assertion. This affects **both** minting (`Entity` → `AddUserId` →
`SignUserId` → `Signature.Sign`) and detached signing (`DetachSign` →
`openpgp.DetachSign` → `Signature.Sign`). The RSA opaque-signer technique
therefore does **not** translate to Ed25519 as-is. Two ways out:

1. **Upstream contribution to go-crypto** — add a `crypto.Signer` fall-through
   to the Ed25519/EdDSA branch of `Signature.Sign` (symmetric with the RSA/ECDSA
   branches). Cleanest long-term; but it puts the feature on an external
   release cadence and a version bump.
2. **In-module manual packet assembly** — compute the Ed25519 signature over the
   OpenPGP digest via the KMS signer ourselves (KMS `ED25519_SHA_512` RAW
   returns the raw 64-byte signature, which *is* the OpenPGP `EdSig` value), and
   assemble the signature packet without going through
   `openpgp.DetachSign`/`AddUserId`. Self-contained, no external dependency, but
   more code and more of go-crypto's framing to reproduce and keep correct.

This decision is the single largest design question in the whole change and is
carried as an open question (§6). Either way, calling the `go/signing` work
"just test coverage" understates it — there is real, security-sensitive code to
write and a path-selection decision to make first.

## 4. Proposed change (additive, RSA retained, per-key choice at mint)

The change is **additive across modules**. Nothing forces existing RSA keys to
move; the algorithm becomes a per-key choice made at mint time. Sequencing
matters because the modules depend on one another.

### 4.1 `go/signing` (do this first — it gates the rest)

- Resolve the go-crypto opaque-signer path (§3.1(b), §6 Q1) before writing the
  backend branch, because the backend's contract depends on it.
- Widen `openpgpkey.Entity` / `WriteArmoredPublicKey` to accept an
  `ed25519.PublicKey` from `signer.Public()` and emit a modern Ed25519
  (algorithm 27) public-key packet via `packet.NewEd25519PublicKey`, building
  the go-crypto `ed25519.PublicKey` from the raw 32-byte key.
- Widen `DetachSign` and `assertSignerMatchesPublicKey` for the Ed25519 signer,
  matching on the Ed25519 public half instead of RSA modulus/exponent.
- Correct the `openpgpkey` package doc: scope the "unreachable / `internal/ecc`"
  statement to the *legacy EdDSA (algo 22)* path and document that the modern
  Ed25519 (algo 27) path is reachable.
- Test coverage: mint → armor → verify round-trip with an Ed25519 opaque signer;
  detached-sign → verify round-trip; fingerprint-mismatch rejection; and the
  reproducibility (deterministic signature) property the RSA path already holds.

### 4.2 `go/signing-aws-kms` (additive Ed25519 backend)

- `newSigner`: accept `ed25519.PublicKey` from `kms:GetPublicKey` alongside
  `*rsa.PublicKey`. Store it in a `crypto.PublicKey`-typed field (the struct
  currently pins `pub *rsa.PublicKey`).
- `Sign`: when the key is Ed25519, call KMS with `ED25519_SHA_512` and
  `MessageType: RAW`, honouring the `crypto.Signer` Ed25519 contract
  (`opts.HashFunc() == crypto.Hash(0)`, message passed as-is). Keep the RSA
  DIGEST path unchanged.
- Return a clear, typed error if a `RAW` message ever exceeds the 4096-byte KMS
  cap, rather than surfacing a raw AWS validation failure. (`ED25519_PH_SHA_512`
  + `DIGEST` is the documented escape hatch if large-payload signing is ever
  required.)
- Flip `TestNewSigner_Ed25519Key_CurrentlyRejected_Issue5` (§2.4) from a
  rejection assertion to an acceptance assertion, and add Ed25519 happy-path +
  algorithm-mapping + oversize-RAW-error tests.
- Correct the stale `awskms.go` / `signer.go` rationale comments.
- Keep RSA fully supported — existing keys and in-field binaries unaffected.

### 4.3 `terraform-aws-signing-kms` (IaC)

- Allow `ECC_NIST_EDWARDS25519` in the `key_spec` variable validation.
- Document it as the preferred spec for **new** keys, with `RSA_4096` retained
  for existing ones. Correct the variable's rationale comment.
- Verify the OIDC signer role's key-policy / `kms:Sign` grant is
  algorithm-agnostic (it should be — the grant is per-key, not per-algorithm).

### 4.4 `go-tool-base` (reference consumer — test + docs, no behavioural change)

- Add an explicit test that a `gtb sign`-produced **Ed25519** signature verifies
  through `pkg/setup`'s self-update verification path (the existing
  `update_signature_test.go` harness already exercises the RSA equivalent).
- Update `docs/how-to/mint-signing-key.md` with a short "choosing a key spec"
  note (Ed25519 preferred for new keys; RSA-4096 retained; a key's algorithm is
  fixed for its lifetime, so switching an existing project is a rotation).
- No behavioural change to `pkg/setup`, `internal/cmd/sign`, or the update path
  is required — they are already `crypto.Signer`/algorithm-agnostic at the call
  site.

### 4.5 Cross-module sequencing

`go/signing` (path decision + signer widening) → `go/signing-aws-kms` (backend,
depends on the signing module's new contract) → `terraform-aws-signing-kms`
(independent, can land in parallel) → `go-tool-base` (bumps both Go modules,
adds the end-to-end test + docs). Publish the two Go modules in lockstep-minor
per the module-versioning convention.

## 5. Acceptance criteria

1. An `ECC_NIST_EDWARDS25519` KMS key can be minted into a valid, verifiable
   armored OpenPGP public key via `gtb keys mint --backend aws-kms`, with the
   KMS private half never materialising.
2. `gtb sign` produces a detached OpenPGP signature over `checksums.txt` using
   an Ed25519 KMS key, and that signature verifies through `go/signing`'s
   `VerifyManifestSignature` and through `pkg/setup`'s self-update path.
3. RSA remains fully supported: existing RSA keys, in-field binaries, and the
   RSA mint/sign/verify round-trip are unaffected (regression tests green).
4. The KMS backend returns a typed error for an oversize `RAW` message rather
   than a raw AWS failure.
5. `terraform-aws-signing-kms` accepts `ECC_NIST_EDWARDS25519` and documents it
   as the preferred spec for new keys.
6. All three stale "KMS does not expose Ed25519" comments, and the
   `openpgpkey` "unreachable" doc note, are corrected (the latter scoped to the
   legacy EdDSA/algo-22 path).
7. `TestNewSigner_Ed25519Key_CurrentlyRejected_Issue5` is updated to assert
   acceptance; new Ed25519 coverage exists in `go/signing` and
   `go/signing-aws-kms`; `go/signing`'s ≥ 90% coverage bar holds.
8. `docs/how-to/mint-signing-key.md` documents the key-spec choice.

## 6. Open questions

1. **go-crypto opaque-signer path (§3.1(b)) — upstream fix vs in-module manual
   assembly?** This gates the entire `go/signing` change. An upstream
   `crypto.Signer` fall-through in go-crypto's Ed25519 signing branch is
   cleanest but couples us to an external release; manual packet assembly is
   self-contained but reproduces more of go-crypto's framing. **Must be resolved
   before implementation starts.**
2. **Algorithm 27 (modern Ed25519, RFC 9580) vs algorithm 22 (legacy EdDSA)?**
   Algo 27 is reachable without `internal/ecc`; algo 22 is what GnuPG 2.4 and
   older import and what `gtb keys generate` currently emits for local Ed25519
   keys. Which does the KMS/production path target, and do we need both for
   consumer-tool compatibility (e.g. `rust-tool-base`, GnuPG-based verifiers)?
3. **Rotation timing.** A rotation is in flight
   (`2026-07-24-prod-rebuild-and-rekey`: v1 abandoned in the old account, v2
   minted in prod). This work must not disturb it; the natural window is after
   that overlap window closes. Do we hold the whole change until then, or land
   `go/signing` + `terraform` (which touch no live key) earlier and gate only the
   backend cut-in?
4. **First-key adopters.** Per D-0010-D each project holds its own key. A project
   minting its *first* key can start on Ed25519 at zero rotation cost — should
   the docs/tooling steer new projects to Ed25519 by default once this lands, or
   keep RSA-4096 the default until a bake-in period passes?
5. **`rust-tool-base` signature-format alignment.** Its verifier is Ed25519-only
   (`ed25519_dalek`, raw 32-byte keys). Does adopting the OpenPGP container
   require anything from the algo-22-vs-27 decision (Q2), or does it consume the
   raw signature independent of OpenPGP framing?
6. **GovCloud / China region coverage.** AWS lists all regions, but the signer
   role, key policy, and Terraform module should be confirmed against the
   partitions any regulated downstream actually deploys to.
